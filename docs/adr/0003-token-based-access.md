# 0003. ログイン無しのトークン共有リンクによるアクセス制御

## ステータス
承認済み

## コンテキスト
要件により、ユーザー登録・ログイン機能は作らない。案件ごとに発行したユニークなURL
(閲覧用リンク/編集用リンク)を知っている人だけがアクセスできればよい。

Supabaseの標準的なRLS(Row Level Security)は `auth.uid()` 等、Supabase Authのセッションを
前提にしたパターンが主流だが、今回はAuthセッションを使わない。anon keyだけでテーブルを
直接公開しつつ、リクエストヘッダー等でトークンを検証するRLSパターンも存在するが、
ポリシー記述が複雑になりやすく、実装ミスがそのまま情報漏洩に直結するリスクがある。

## 検討した選択肢
- **A: テーブルを直接anon keyに公開し、ヘッダー/クエリパラメータのトークンをRLSポリシーで検証**
  - PostgRESTの `request.headers` 経由でトークンをRLS内から参照できる
  - 長所: PostgRESTの自動生成REST APIをそのまま使える
  - 短所: ポリシー記述のミスが即座に全データ漏洩につながる。ヘッダーの受け渡し経路(Next.js側の実装ミス)も攻撃面になる
- **B: テーブルはRLSで完全非公開(anon roleに対してdenyがデフォルト)にし、
  `SECURITY DEFINER` のPostgres関数(RPC)経由でのみ読み書きさせる**
  - 関数の引数でトークンを受け取り、関数内で明示的に検証してからテーブル操作する
  - 長所: 検証ロジックが1箇所(関数)に閉じる。テーブルへの「抜け道」が存在しない
  - 短所: CRUDのたびに関数を書く必要があり、PostgRESTの自動生成の恩恵を受けにくい
- → Bを採用。想定同時アクセス数が小さく、関数の本数もそれほど多くならない見込みのため、
  「抜け道を作らない」安全性を優先する

## 決定
- 全テーブルでRLSを有効化し、anon roleに対するポリシーは基本的に何も許可しない(deny by default)
- クライアントからのデータ読み書きは、以下のような `SECURITY DEFINER` 関数経由のみに限定する
  - `get_project_by_view_token(token uuid)` — 閲覧用: 案件情報とピン一覧を返す
  - `upsert_pin_by_edit_token(token uuid, pin jsonb)` — 編集用: ピンの追加・更新
  - `delete_pin_by_edit_token(token uuid, pin_id uuid)` — 編集用: ピンの削除
- 各関数の冒頭で、渡されたトークンが対象案件の `view_token`/`edit_token` と一致するかを検証し、
  一致しなければ例外を投げて終了する
- トークンはUUID(v4相当のランダム値)を使用し、推測困難性を確保する
- URLの形式は `/p/[view_token]`(閲覧)、`/p/[view_token]/edit/[edit_token]`(編集)を基本とする

## 結果・トレードオフ
- 関数を追加するたびに「トークン検証を書き忘れる」リスクは残るため、レビュー時(Reviewer役)は
  新規関数に必ずトークン検証があるかを重点的に確認する
- PostgRESTの自動CRUD生成は使わないため、型生成(supabase gen types等)は関数の戻り値型に
  対して行う
- 将来、正式なSupabase Authでのログイン機能に移行する場合も、関数の内部実装を差し替えるだけで
  フロントエンドのインターフェースを変えずに済む見込み
