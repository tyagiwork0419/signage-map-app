# 0004. 同時編集時のデータ競合対策

## ステータス
承認済み

## コンテキスト
1案件あたり同時アクセスは10箇所程度の想定で、処理負荷そのものは問題にならない。一方で、
複数人が同じピンをほぼ同時に編集した場合に、後勝ち(last write wins)で片方の変更が
無言で消えると、現場での混乱につながる。

## 検討した選択肢
- **A: 何もしない(単純な後勝ち)**
  - 実装は最も簡単だが、変更が無言で消えるリスクをそのまま許容することになる
- **B: 楽観的ロック(バージョン番号 or updated_at の比較)**
  - 更新時に「自分が最後に読んだ時点のバージョン」を一緒に送り、DB側で一致しなければ
    更新を拒否してクライアントに競合を通知する
  - 長所: 実装がシンプルで、想定規模(10箇所程度)には十分。データが消えることはなく、
    「誰かが後から変更したので最新の内容を確認してください」という形でユーザーに委ねられる
  - 短所: 真の意味での自動マージはしない(競合したら人間が選び直す)
- **C: リアルタイム協調編集(CRDT等)**
  - 過剰。今回の規模・用途(ピンの位置決め)には見合わない実装コスト
- → Bを採用

## 決定
- `pins` テーブルに `updated_at`(タイムスタンプ)を持たせる
- 更新系のRPC関数(`upsert_pin_by_edit_token`)は、クライアントから送られてきた
  「編集を開始した時点の `updated_at`」を受け取り、現在のDB上の `updated_at` と比較する
  - 一致すれば更新を許可し、`updated_at` を更新する
  - 不一致であれば更新を拒否し、クライアントには「他の人が更新しました」という
    競合エラーを返す。クライアント側は最新のデータを再取得してユーザーに提示し、
    上書きするかどうかを選ばせる
- 新規ピンの追加(競合が起こりようがない操作)には、このチェックは不要

## 結果・トレードオフ
- 実装コストは小さく、想定規模に見合っている
- 自動マージはしないため、「同じピンを複数人がほぼ同時に動かす」場面では、
  後から編集した側が一度エラーを見て操作し直す手間が発生する(許容範囲と判断)
- 将来、同時編集頻度が上がってきた場合は、Supabase Realtimeを使った
  「他の人が今このピンを編集中です」という表示の追加を検討する(今回はスコープ外)
